## 二、仍需修复的问题

### R3-P0-1：flush-only 语音段可能被误判为无语音

**严重程度**：高
**涉及文件**：

- `experiments/scripts/run_exp_latency.py:645-659`
- `src/asr/streamaudio_segmenter.py:240-245, 286-303`

当前 `run_exp_latency.py` 只在以下条件成立时把 flush 段当作最终含语音段：

```python
if remaining_segment.is_speaking:
    last_speech_commit = flush_commit
```

但 `StreamAudioSegmenter.flush()` 中的 `is_speaking` 来自 `state.is_speaking`，它表示最近一次 VAD 状态，不一定表示 `state.accumulated_audio` 中是否仍然存在未完成的语音段。

一种可能的边界流程是：

1. 前面的音频已经检测到语音，但语音段尚未闭合；
2. 后续静音 chunk 使 `state.is_speaking = False`；
3. `state.accumulated_audio` 仍保留未 flush 的语音/残余音频；
4. `flush()` 返回该残余段，但 `remaining_segment.is_speaking == False`；
5. `final_speech_segment_commit_time` 保持 `0.0`；
6. 结果层错误标记 `asr_no_speech`。

这会把真实语音样本排除出 endpoint 统计，并可能影响 E5 的有效样本数和 TTFA 预算。

**修改建议**：

不要单独使用 `remaining_segment.is_speaking` 判断 flush 段是否含语音。建议在分段状态中增加显式的“是否检测到过语音/当前缓冲是否属于语音段”状态，例如：

```python
StreamState.has_detected_speech: bool = False
StreamState.pending_speech: bool = False
```

当 VAD 首次检测到 speech timestamp 时设置 `has_detected_speech=True`；当语音段被闭合或 flush 时，根据该状态判断最终段是否属于语音。或者在 `AudioSegment` 中增加明确字段：

```text
contains_speech
```

之后使用：

```python
if remaining_segment.contains_speech:
    last_speech_commit = flush_commit
```

`is_speaking` 可以继续表示当前 VAD 状态，但不要把它当成历史缓冲内容是否含语音的判据。

**必须增加的回归测试**：

构造一个“语音开始但没有在普通 process_audio 阶段闭合，随后出现静音，最后由 flush 输出”的样本，确认：

- `final_speech_segment_commit_time != 0.0`；
- 不会标记 `asr_no_speech`；
- 纯静音和极短无效音频仍然保持 `final_speech_segment_commit_time == 0.0`；
- `final_is_final_segment_enqueue_time` 仍记录 final 段入队时间。

这一测试必须进入仓库中的可执行测试脚本或最小回归命令，而不能只写在回复文档中。

### R3-P1-1：clean source 脚本仍硬编码当前样本数量

**严重程度**：中
**涉及文件**：`experiments/scripts/make_exp2_clean_source.py:约112`

本轮已经把 dated 输入输出路径改成 CLI 参数，这是正确的。但脚本仍然存在类似：

```python
assert len(clean_rows) == 498 and len(excl_rows) == 7
```

这意味着：

- 更换一批 exp2 结果；
- 使用另一份样本清单；
- 重新运行不同规模的实验；

脚本仍会因为样本数变化而失败，需要再次编辑源代码。因此该脚本只是“路径参数化”，还不是真正可复用。

**修改建议**：

把当前数据集数量从硬断言改成配置或动态校验：

1. 如果数量由 sample list 决定，应检查：

```python
len(clean_rows) == len(sample_list)
```

2. 如果保留当前归档的审计校验，增加显式参数：

```text
--expected-clean-count
--expected-exclusion-count
```

默认不设置时不校验固定数量；设置时才执行审计断言。

3. `exp2_gains_clean.meta.json` 中记录：

- sample list 数量；
- 实际 clean 数量；
- 实际 exclusion 数量；
- 若启用 expected count，记录期望值。

当前 498/7 的旧归档验证可以保留为一次特定数据集校验，但不能写成脚本对所有输入的硬编码前提。
