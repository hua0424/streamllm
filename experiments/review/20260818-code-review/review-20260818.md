## 1. 总体结论

当前代码已经完成语法检查，DEV-1/2/3/4/5 的基础冒烟路径也曾在本机小模型环境中跑通。但在正式 GPU 实验前，仍需完成本文档列出的整改。

最重要的原因不是程序是否能跑通，而是：

- 某些实验结果尚不能直接满足论文计划中的统计字段；
- 某些时间字段的实际含义与实验计划定义不一致；
- 某些异常路径在小样本冒烟中没有出现，但在全量 GPU 实验中可能导致失败或产生不可审计的数据；
- 部分统计结果能够计算，但输入完整性和样本口径没有被程序强制验证。

**正式 GPU 实验建议**：环境初始化、模型下载、数据包验收可以继续；E3 LocalAgreement 和 E5 端点等待正式运行应在 P0 问题处理并完成回归测试后开始。

**处理决定**：

### 2.2 Table IV 使用新清单重算是可接受的

Table IV 原始排除依据没有落盘，无法完整复现旧的手工修复过程。但新清单已经把排除规则显式化：

- 任一模式运行错误的样本成对排除；
- 任一流式模式 TTFT > 10,000 ms 的挂起样本成对排除；
- 保留同一样本的三种模式进行 paired comparison。

重算后的均值与论文原值差距较小，定性结论不变，因此可以作为修改稿 Table IV 的新统计口径。论文和回复信中需要明确这是一次按可复现规则重算，而不是声称复原了旧的手工排除列表。

## 3. P0：正式 GPU 实验前必须整改

### P0-1：LocalAgreement 基线没有计算 WER/CER

**涉及文件**：

- `experiments/scripts/run_exp_baseline_la.py:191-203`
- `experiments/scripts/run_exp_baseline_la.py:250-265`

**问题**：

当前 LA 基线结果只记录：

- `ttft`
- `asr_time`
- `llm_prefill_time`
- `transcribed_text`
- `full_response` / `response_preview`

但实验计划中 R3 要求的交付物是：

> `System A / LA-streaming / System B` 的 TTFT mean±std 与 WER/CER。

当前脚本没有把 `SampleInfo.text` 作为 reference，也没有复用 `run_exp_quality.py` 中已有的文本归一化、中文分词、WER/CER 计算逻辑。因此 E3 即使成功跑完，也不能生成论文计划中的 Table VII，也无法比较 LA 与 System B 的识别质量差异。

**修改建议**：

1. 复用 `experiments/scripts/run_exp_quality.py` 中已有的：
   - `normalize_text`
   - `wer`
   - `cer`
   - `zh_to_word_seq` 或等价中文分词逻辑
2. 在每个 LA 样本完成后，以 `sample.text` 为 reference、`result.transcribed_text` 为 hypothesis 计算：
   - 英文：至少 WER，保留 CER 便于完整报告；
   - 中文：至少 CER，保留 WER 便于与现有质量实验统一。
3. 将 `wer`、`cer` 写入：
   - 逐样本 JSON；
   - `la_summary_*.csv`；
   - 分组统计 CSV 或单独的 quality statistics 文件。
4. 对空转写单独标记 `asr_no_text`，不能把空文本当作普通 WER/CER 结果静默纳入。

**理由**：

R3 不是单纯的延迟实验。审稿人要求比较 LocalAgreement 基线时，需要知道 LA 的延迟代价和质量代价。只有 TTFT 没有 WER/CER，实验结论不完整。

**验收标准**：

- 用 2 个样本冒烟运行后，结果 JSON 每条包含 `wer`、`cer`；
- CSV 包含对应列；
- 至少有一条英文和一条中文样本时，离线计算结果与 `run_exp_quality.py` 的同一归一化逻辑一致；
- 运行错误或空转写不会产生看似正常的质量数字。

### P0-2：`final_segment_commit_time` 的实际含义与计划定义不一致

**涉及文件**：

- `experiments/scripts/run_exp_latency.py:628-651`
- `experiments/scripts/run_exp_latency.py:759-760`
- `experiments/CISR_REVISION_PLAN.md` R6.1
- `experiments/GPU_EXPERIMENT_HANDOFF.md` DEV-1/E5

**计划定义**：

计划要求记录：

> `final_segment_commit_time`：分段器把 `is_final=True` 的段放入 `audio_segment_queue` 的时刻。

当前实现记录的是 `last_speech_commit`，即最近一次 VAD 识别出完整语音段并入队的时间。flush 生成的最终 `is_final=True` 段没有使用同一个时间字段记录。

因此当前 `endpoint_wait` 实际表示：

```text
最后一个 VAD 语音段关闭时间 - speech_end_time
```

而不是计划定义的：

```text
最终 is_final 段入 audio_segment_queue 的时间 - speech_end_time
```

两者在尾部追加 2 秒静音时可能明显不同。当前本机冒烟约 0.18 秒，不能直接据此证明计划定义的 final enqueue wait 也是 0.18 秒。

**修改建议：二选一，但必须统一命名、代码、计划和论文口径。推荐方案是同时保留两个时间点：**

```text
final_speech_segment_commit_time
final_is_final_segment_enqueue_time
```

建议实现：

1. 在普通 VAD 段入 `audio_segment_queue` 后记录普通段入队时间；
2. 在 flush 产生的 `is_final=True` 段入队后，记录 `final_is_final_segment_enqueue_time`；
3. 如果需要衡量真实端点检测等待，则使用：

```text
endpoint_detection_wait = final_speech_segment_commit_time - speech_end_time
```

4. 如果严格按照原 handoff 规格，则使用：

```text
final_enqueue_wait = final_is_final_segment_enqueue_time - speech_end_time
```

5. 两个字段都写入结果 JSON，并在 `RUNINFO.md` 或统计脚本中说明论文最终采用哪一个。

**理由**：

时间指标名称必须反映真实事件。否则论文中“端点等待”“最终段提交”和“语音结束”的定义会相互混淆，审稿人无法复核 TTFA 分解。

**验收标准**：

- `append-silence-ms=2000` 冒烟时两个时间点都非零；
- `audio_end_time - speech_end_time` 约等于 2 秒；
- 结果中可以明确计算两种 wait；
- E5 命令和论文使用的统计口径不依赖读者猜测。

### P0-3：LA 空尾片段可能导致 LLM 增量缓存失败

**涉及文件**：

- `experiments/scripts/run_exp_baseline_la.py:154-159`
- `src/llm/stream_llm_inference.py:266-280`

当前代码：

```python
tail = self.la_streamer.flush()
text_queue.put((tail, True))
```

LLM worker 随后会因为 `is_end=True` 调用：

```python
kv_cache = self.llm.cache_prompt(text, pre_cache=kv_cache, is_end=is_end)
```

如果 `tail == ""`，且之前已经有增量文本，那么 `_add_stream_prompt()` 会收到空字符串并抛出“要添加的文本为空”异常。

该路径在 2 个 tiny 冒烟样本中没有触发，但全量数据中完全可能出现“最后一轮没有新文本”的情况。

**修改建议**：

建议显式区分“追加文本”和“结束生成”：

- `tail` 非空：发送 `(tail, True)`；
- `tail` 为空但已有 `kv_cache`：调用一个明确的结束/生成路径，不要把空字符串送入 `_add_stream_prompt()`；
- `tail` 为空且没有任何有效文本：记录 `asr_no_text` 或 `empty_prompt`，按实验预定义策略处理，不能静默生成无意义结果。

可以在 `StreamLLMInference` 中增加一个只负责结束 prompt 的安全接口，也可以在 LA worker 中确保最后一次有文本的 cache 已经通过 `is_end=True` 完成收尾，但必须配合单元测试验证。

**验收标准**：

至少覆盖以下 3 种测试：

1. 有增量文本，flush 返回空字符串；
2. 无增量文本，flush 返回非空字符串；
3. 全程无文本。

三种情况均不能出现空文本传给 `_add_stream_prompt()` 的异常路径。

### P0-4：TTS 测量脚本会静默使用截断的 response_preview

**涉及文件**：

- `experiments/scripts/measure_tts_first_chunk.py:147-156`

当前逻辑：

```python
text = r.get("full_response") or r.get("response_preview", "")
```

如果 GPU 机 E4 忘记使用 `--save-full-response`，脚本会自动把最多 100 字符的 `response_preview` 当成完整回复送给 TTS。

这会导致：

- TTS 输入文本被截断；
- 音频时长分布偏短；
- TTFC、总时长和 RTF 的统计失真；
- 脚本仍然“成功运行”，问题不容易被发现。

**修改建议**：

正式实验模式下，如果结果中没有 `full_response`，应直接失败并提示：

```text
E4 result does not contain full_response; rerun with --save-full-response
```

如果确实需要 preview fallback，应增加显式参数，例如：

```text
--allow-preview-fallback
```

默认关闭。并且输出 CSV 和 RUNINFO 中必须记录是否使用了 fallback。

**验收标准**：

- 输入只有 `response_preview` 时，默认命令退出非零；
- 输入含 `full_response` 时正常抽取；
- `--allow-preview-fallback` 模式下 CSV 标记 `text_source=preview`，不能与完整回复混淆。

## 4. P1：应在正式实验前处理

### P1-1：Table IV 重算缺少三模式完整性校验

**涉及文件**：`experiments/scripts/recompute_stats.py:108-143`

当前 Table IV 直接按照 `exp2_ablation_sample_list.json` 过滤结果并计算均值，没有强制检查每个样本是否同时具有：

- `baseline`
- `streaming_asr_only`
- `full_streaming`

也没有检查三种模式的：

- `audio_duration` 是否一致；
- 是否全部无 error；
- 是否每种模式恰好一条记录。

如果某次结果 JSON 不完整，脚本可能仍然输出一个数字，造成样本数不一致或非 paired 统计。

**修改建议**：

在 Table IV 重算前建立 `sample_id -> mode -> result` 索引，并强制检查：

```text
每个 sample_id 恰好有三种模式
所有模式 error 为空
audio_duration 差异在容差内
```

任何失败都应直接报错并列出 sample_id，不应静默跳过。

**验收标准**：

- 对现有 exp2 JSON 检查通过；
- 删除一条 full_streaming 记录后，脚本非零退出并指出具体样本；
- 统计输出中每个分组的三个模式 n 完全一致。

### P1-2：Table III 的 paired filtering 改变了 baseline 样本口径，需要显式记录

**涉及文件**：`experiments/scripts/recompute_stats.py:66-83`

当前逻辑只要某个样本的 streaming 或 non-streaming 出错，就把该样本两种模式一起排除。这对于 paired comparison 是正确的，但会改变 baseline 的 n 和均值。

当前重算中：

- streaming Long+ 均值基本保持原值；
- 对应 baseline 的某些分组均值有轻微变化；
- Extra Long baseline 从旧值约 6753.43 ms 变化为约 6745.57 ms。

**修改建议**：

输出文件中增加：

- `excluded_sample_ids` 或单独的 `filter_manifest.json`；
- 每组原始 n、排除 n、最终 n；
- 排除原因（runtime error / hang outlier）。

论文和回复信中表述为：

> 为保证模式间成对比较，重算时排除对应模式不完整的样本，因此 baseline 的样本数和均值可能出现轻微变化。

不能同时声称所有旧均值都未改变。

### P1-3：LocalAgreement 前缀修正时可能发生状态失配

**涉及文件**：`src/asr/local_agreement_streamer.py:109-137`

当前 LA 使用：

```python
agreed[self.n_committed:]
```

如果新一轮识别结果改变了已提交词之前的内容，最长公共前缀长度可能小于 `n_committed`。此时：

- 已提交计数仍保留旧值；
- 后续文本可能持续无法提交；
- 状态失配不会被显式记录。

这属于 LA 基线必须观测的边界情况，不能只依赖“正常情况下不会发生”。

**修改建议**：

1. 当 `len(agreed) < n_committed` 时追加 correction/divergence event；
2. 不要继续用失配的 `n_committed` 静默推进；
3. 设计明确的恢复策略，例如重新对齐到当前公共前缀、重置未提交状态，或标记该样本为 correction case；
4. 将 correction count 写入 LA 结果 JSON/CSV。

**验收标准**：

用 mock model 模拟以下序列：

```text
round 1: hello world
round 2: hello word
round 3: hello word again
```

验证：

- divergence 被记录；
- 状态不会永久卡住；
- 输出文本没有静默重复或丢失。

### 第二步：本机回归测试

必须至少运行：

```bash
uv run python -m py_compile \
  experiments/scripts/recompute_stats.py \
  experiments/scripts/measure_tts_first_chunk.py \
```

```bash
HF_TOKEN= uv run python -m experiments.scripts.run_exp_baseline_la \

  --save-full-response \
  --save-fragments \
```

```bash
HF_TOKEN= uv run python -m experiments.scripts.run_exp_latency \
```

TTS fallback 回归：

- 构造只有 `response_preview` 的 E4 JSON；默认必须失败；

- 删除 exp2 某样本的一个模式后，`recompute_stats.py` 必须非零退出；
- 修改一个模式的 audio duration 后，必须报 paired mismatch；
- 现有完整 exp2 JSON 必须正常通过。
