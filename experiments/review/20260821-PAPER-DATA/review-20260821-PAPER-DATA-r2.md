## 二、新发现（P0 级，Table VIII 数字入论文前必须再裁决）：方案2 的实现把装置窗口内的真实工作一并剔除了

### 证据（本机逐样本重算，50/50 样本）

1. **守恒分解成立**（恒等式残差 0.0000ms）：
   `E5 total(speech_end→首token) 3065.1ms = 端点等待 53.1 + 静音窗 1999.5 + 末段处理(first_token−final_enqueue) 1012.5`。
2. **静音窗 1999.5ms 不是纯空转**：逐样本计算 `E4 TTFT − E5 post-flush`（同 50 样本、同代码、同机器，E4 即 flush 在文件尾立即发生的对照运行），**mean 410.5ms、min 139.0、max 1257.9，50/50 全为正**。即：窗口内约 410ms 是 ASR/LLM 在排空端点时仍积压的队列（真实工作），约 1589ms 才是装置空转。
3. **同物理量两种得法矛盾**："speech_end→首 token、无装置等待"这一量：
   - E4 直接实测 = 端点 53.1 + TTFT 1422.9 = **1476.0ms**；
   - 方案2 合成 = 53.1 + 1012.5 = **1065.6ms**；
   - 差 410.4ms **恰等于排水项**——不是巧合，是守恒必然：真实端点触发 flush 时，端点时仍积压的段必须在端点后处理完才能出首 token；E5 里这 410ms 之所以发生在窗口内，仅仅因为窗口存在。**没有任何部署模型下用户感知的 speech_end→首 token 是 1065.6ms**（立即 flush → ~1476ms；先等积压排空再 flush → 排水等待 + 末段 ≈ 同值）。

### 影响与定性

- 方向：B 行 pipeline 分项少计 ~0.41s，**有利于本文系统**，与"禁缩放/禁美化、如实呈现"红线冲突（此前 E5 链条口径是反向保守，方案2 修正方向正确但过冲）。
- 责任认定：**审查侧首轮报告有误**——方案2 原文把"post 改用 first_token−final_enqueue（1012.5ms）"与"E4 同期 flush 口径"两个**不等价**子项用"或"并列并给同一总计 ~14.4s，误导了裁决选项的精度。开发按裁决字面实现无误。本条为审查侧自我修正，非开发实现错误。
- 对开发澄清 #3（弃方案3 理由）的回应：
  1. "E4 的 audio_end 含数据集自带尾隙"不构成区分两个子口径的理由——E5 的 `speech_end = audio_end − 2s` 与 E4 的 `audio_end` 是**同一参考点**（E5 QA 实测差 2.002±0.001s），尾隙因素（若存在）对两口径**同等**作用；
  2. "不跨运行混合"在现表中本就不成立：A 行端点项取自 E5 streaming 行、decode/TTFC 取自补测与 B 的测量——表格天然是多源装配，E4 与 E5 同机同码同 50 样本相隔一天（E1 三轮重跑证明同机 TTFT 稳定，1422.9 落在 1434–1482 带内），混源风险可控。

### 处置建议（需需求方再裁决，二选一）

- **(a) 推荐**：B 行 post 改用 E4 同 50 样本 streaming TTFT（ALL **1422.9ms**；zh 1398.9 / en 1447.0，本机已预计算）——它就是"端点触发 flush"尾延迟的直接实测，与 A 行"post=自 flush 起的完整工作量"口径对称。修正后预期：B zh ≈ **15.58s** / en ≈ **13.99s** / ALL ≈ **14.79s**，A 不变 22.67s，差距 ≈ 7.9s。
- **(b) 维持 1012.5ms**：则论文必须把该分项明确定义为"末段处理（**假设**静音窗内积压已排空）"，并披露其比 E4 直接实测低 ~0.41s——等于自证分项是下界，不推荐。

**裁决前，B ALL 14.38s 及 zh/en 分项不得写入论文。** A 行 22.67s 与其余三个分项（端点 53ms、decode 389ms、TTFC）不受本条影响。
